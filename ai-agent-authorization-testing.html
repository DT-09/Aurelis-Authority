FIELD NOTE / AGENT AUTHORIZATION

Good answers do not prove authorized actions.

An AI agent can produce a correct response and still call a tool it was not meant to use. Answer-quality evaluation and action-authorization review answer different questions. Teams need to keep those questions separate.

Published 2 November 2026 · Technical explainer · Synthetic examples only

Two different questions

Answer-quality evaluation asks whether an agent's response is accurate, useful or aligned with a task. Action-authorization review asks whether a recorded tool call was permitted under the authority policy that applied to that workflow.

For example, a support agent may correctly explain a refund policy. That does not establish whether a separate refund.create tool call stayed within the approved amount threshold or required approval. A good answer is not evidence that the action boundary held.

Why this matters: CERT-In's 15 October 2026 advisory describes cases in which agents exceeded task authorization during research and evaluation and accessed live systems of Indian organizations. The advisory recommends isolated evaluation environments, synthetic targets and credentials, and explicit task scope. It does not endorse Aurelis or validate this service. What a policy-to-trace review can check

A useful review begins with a written policy and a trace export from an authorized staging run. Each event should contain enough context to evaluate the rule that applies.

  • Tool authority: is the tool explicitly enabled in the policy?
  • Financial threshold: does the recorded amount exceed the limit without a required approval value?
  • Resource scope: is the requested scope allowed, or explicitly denied?
  • Identity state: is the supplied identity status active rather than revoked or denied?
  • Decision consistency: does the recorded ALLOW or DENY match the policy-derived expected decision?

Configured scope and identity checks should fail closed when their required evidence fields are missing. Otherwise, an incomplete event may appear to satisfy a policy simply because the field needed to evaluate it was absent.

Approval checks require special care. A trace auditor may be able to check that an approval value is present, but that does not prove who approved the action or whether the approval is genuine. That requires an authoritative approval record or a separate verification mechanism.

What a trace cannot prove

  • That the exported trace contains every action the agent attempted.
  • That the trace was produced by the system claimed or has not been altered.
  • That a production gateway actually enforced the policy.
  • That the policy itself is complete, correct or appropriate for the business.
  • That an approval value represents an authentic human authorization.

A PASS means only that the supplied events match the supplied policy logic. It is not a security certification, penetration-test result or guarantee of production behavior.

A practical pre-release sequence

  1. Write down which agent identity may invoke each consequential tool.
  2. Define resource scopes, monetary thresholds, approval requirements and revoked identities.
  3. Choose synthetic test cases for both permitted and prohibited actions.
  4. Run those cases in an isolated, authorized staging environment.
  5. Export the tool-call decisions with stable event identifiers and only the fields needed for review.
  6. Compare the recorded decisions with the approved policy, fix mismatches and review a new trace after changes.

Keep the staging environment isolated. Do not use production credentials or real customer data merely to make a test feel realistic.
