AURELIS AUTHORITY / SERVICE SCOPE

AI agent authority, reviewed against the trace.

Aurelis performs a focused, policy-based review of exported AI-agent tool-call traces. We compare the decisions recorded in a staging run with the authority rules approved by your team, identify mismatches, and produce an evidence-linked report with a retest review.

Important scope boundary: the current service is an offline trace audit. Your team runs agreed test cases in its own authorized staging environment and supplies sanitized records. Aurelis does not connect to, intercept, or block a live agent.

01 / INPUT

Approved policy + exported trace

A versioned authority policy and a sanitized JSON trace containing event IDs, tool names, arguments and recorded ALLOW or DENY decisions.

02 / ANALYSIS

Expected versus observed

Each supplied event is evaluated against supported policy rules. The report separates matching decisions, unexpected allows, unexpected denies and invalid inputs.

03 / OUTPUT

Evidence-linked findings

Receive a machine-readable result with event references, policy reasons, mismatch classification, summary counts and explicit evidence limitations.

04 / FOLLOW-THROUGH

One repeat audit

After your team changes its controls, supply a second trace. Aurelis evaluates it against the agreed policy version and records whether the observed decisions changed.

WHAT THE REVIEW CHECKS

Make the action boundary explicit.

The current version-1 policy model supports checks such as:

  • Whether a tool is enabled in the approved policy.
  • Whether a recorded amount exceeds a configured threshold without a required approval value.
  • Whether a supplied resource scope appears in a denied-scope list.
  • Whether a supplied identity status appears in a revoked or denied status list.
  • Whether the recorded decision matches the policy-derived expected decision.
Approval limitation: the current auditor checks only whether a configured approval field is non-empty. It does not authenticate the approver, validate a signature, or verify an external approval record.

DEVELOPER WORKFLOW / CI

Run policy checks in GitHub Actions.

The open-source trace checker can run in a CI workflow against a policy file and an exported JSON trace. It exits with a non-zero status when an unexpected ALLOW is found or when the input is invalid. This is a self-service check of supplied records, not a live control or independent audit.

HOW THE AUDIT WORKS

Six steps. No production credentials.

  1. Scope: identify one agent, one consequential workflow, the policy owner and the evidence boundary.
  2. Define: agree the authority policy, policy version and expected decisions.
  3. Run: your team executes agreed cases in its own authorized staging environment.
  4. Export: provide a sanitized trace and the field mapping needed to interpret it.
  5. Audit: Aurelis validates the inputs, compares recorded decisions with policy expectations and documents findings.
  6. Re-audit: after remediation, provide one retest export for comparison against the agreed policy.

PILOT FIT

Who should use this?

The first pilot is intended for an AI product team or implementation agency that already operates a tool-using agent and can export staging traces. It is most relevant where a workflow can issue refunds, change records, access restricted data, trigger approvals or call consequential business APIs.

A good fit has a named technical owner, a written authority policy (or a person authorized to approve one), and a current release or deployment where an independent evidence review would help.

A poor fit is a team that needs live interception, a penetration test, a certification, a guarantee of system security, or an assessment without usable trace exports. Those are outside the current service.

DATA HANDLING & LIMITATIONS

Know what the evidence cannot prove.

  • The public workspace evaluates supplied records per request and does not persist submitted traces through the audit endpoint.
  • Do not submit credentials, secrets, production payment data or unnecessary personal information.
  • The audit does not authenticate the source of events or prove that the supplied trace is complete.
  • A matching decision means the supplied event matches the configured policy logic; it is not a security certification or proof of safe production behavior.
  • Results apply only to the supplied records, policy version and documented assumptions.

FREQUENT QUESTIONS

Before you request a review.

Does Aurelis connect to our agent?

No. The current service reviews exported traces. Your team runs the agreed cases in its own authorized staging environment and supplies sanitized records.

What file formats are supported?

The current public workspace accepts JSON policy and trace inputs using the documented version-1 schema. Other trace formats require a field mapping or separately agreed preparation work.

Can Aurelis confirm that an approval was genuine?

No. The current policy checker can require a non-empty approval value, but it does not authenticate the approver or validate an external approval record.

Is this a penetration test or certification?

No. It is a bounded offline policy-to-trace review. It does not replace penetration testing, runtime enforcement, compliance assessment or a security certification.

What is needed to begin?

One workflow description, one approved policy, a sanitized staging trace, the trace field mapping and a technical contact who can clarify the records.
